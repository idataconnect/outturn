# The OpenAPI wizard

Turning a specification into something an agent can use, without paying for the
specification on every turn.

Designed, unbuilt.

## Why this first

An integration needs three things: a host the workspace is allowed to reach, a
credential bound to it, and a skill saying what to call. `fetch_url` supplies
the calling, so the only part that is real work is the skill -- and writing good
skill text for an API by hand is tedious enough that it does not get done.

Most services already have an OpenAPI document, often generated by the framework
they are built on and served for free. Where one does not exist it can be
written by hand against a REST service, and a partial document covering the
three endpoints somebody actually needs is far less work than writing the prose
those three endpoints deserve.

## The constraint that shapes everything

A skill body is composed into the system prompt (`skill::compose`) and is
therefore paid for on **every round of every turn, for the life of the
session**. That is the whole design problem.

A real specification is enormous. Stripe's runs to several megabytes; an
ordinary internal API has hundreds of operations, each with parameters,
constraints, a request schema and several response schemas. Rendering one
faithfully into a skill body produces something nobody can afford to carry, and
trimming it by hand puts the work back where it started.

So the wizard does not translate a specification into prose. It splits it in
two.

## Manifest and detail

The same shape the guest's own tools already use. `load_tools` offers the model
a list of names and hands over the definitions when they are asked for, because
a tool that is not being used should not be occupying the prompt. An API's
operations are the same problem at a larger scale.

**The manifest is the skill body.** One line per operation: a name, what it is
for, and where to read the rest. It is what sits in the prompt, and it is small
enough to carry every turn even for a large API.

**The detail is a file per operation**, written to the object store. The full
parameter list with types and constraints, the request shape, what comes back,
and the errors worth handling. The agent reads it with `read_object` when it
decides it needs that operation, and pays for it only then.

Nothing new is required for any of this. `read_object` exists, the object store
exists, and `PUT /v1/agent-sessions/{id}/files/{scope}/{path}` is how something
above writes a file an agent can read.

### Where the files go

`workspace/` scope, which is **read-only to an agent by default**
([storage.md](storage.md)) -- the right default for reference material an agent
consults and must never rewrite. It is also shared, so one wizard run serves
every agent in the workspace rather than being copied per agent.

A layout that reads well in a listing and in a path:

```
workspace/api/<service>/index.md         the manifest, mirrored from the skill body
workspace/api/<service>/<operation>.md   one file per operation
```

The operation file name is the operation's name in the manifest, so an agent
that has read the manifest can construct the path without being told it
separately. That matters more than it looks: a path the model derives is a path
it gets right, where a path it has to remember from elsewhere in the prompt is
one it invents.

## What the manifest line says

Enough to choose an operation, and not enough to call it. That division is the
point -- a line that tried to be sufficient would be the specification again.

```
- `create_booking` — Reserve a room for a date range. Detail:
  workspace/api/hollowbrook/create_booking.md
```

A name, a sentence, a path. The name is derived from `operationId` where the
specification has one and from the method and path where it does not, because
`operationId` is optional and frequently absent.

**Names, not URLs, in the manifest.** This is the failure
[skill-evaluation.md](skill-evaluation.md) was written about: a skill that
documents its call the way an API reference does -- `GET
https://api.example.com/bookings` -- reads correctly to a capable model and gets
called as a tool name by a weaker one. The manifest therefore never shows a URL.
A URL appears for the first time inside the detail file, in the company of the
method, the parameters and an explicit instruction to use `fetch_url`, where
there is enough context for it to be unambiguous.

## What the detail file says

The operation, in the order somebody would need it:

- What it does, in a sentence.
- The call: method and full URL, with path parameters marked.
- Parameters: required ones first, each with its type and any constraint the
  specification states. Optional ones after, and only those with a described
  effect -- an optional parameter nobody can explain is noise.
- The request body's shape, where there is one.
- What comes back on success, as a shape rather than a schema: the fields worth
  reading, not the full response object.
- The errors worth handling, and what they mean.

Response schemas are where a faithful rendering goes wrong most often. A
specification describes every field of a resource; an agent needs the handful it
will act on. The wizard should render the success shape at one level of depth
and say that more is available, rather than inlining a nested object graph.

## Worked examples arrive later, and are observed rather than written

The obvious thing to put in a detail file is an example call. The wizard should
not write one, because a generated example is a guess about what a model will
do with the operation, and a guess in a file the agent trusts is worse than no
example.

Examples come from evaluation ([skill-evaluation.md](skill-evaluation.md)).
When a real turn calls an operation successfully, that call is evidence rather
than conjecture -- and it attaches to the detail file, which is the same unit
the agent already fetches. So the mechanism needs nothing added: an example is
appended to a file that is already lazily loaded.

That ordering is deliberate. The wizard ships first and produces skills without
examples; evaluation improves them afterwards from what actually happened. A
wizard that invented examples first would have to be unwound.

## Everything, by default

Because the prompt no longer grows with the specification, there is no reason
to make the workspace choose which operations to include. Include them all,
write a file each, and let the manifest carry the names.

That is not merely easier. A workspace choosing up front has to predict what
its agents will need, and it will be wrong in the direction of omission -- the
operation nobody selected is the one the agent turns out to need, and its
absence is invisible. Including everything makes the manifest the only thing
that grows, and a long manifest is a cost that can be measured and trimmed
later against real usage rather than guessed at now.

A very large specification may still produce a manifest worth splitting. The
natural seam is the specification's own tags, which usually group operations the
way the API's authors thought about them -- one skill per tag, each with its own
manifest. Worth doing when somebody hits it, not before.

## Hosts and credentials

The wizard reads `servers` and records each host in `skill_version_hosts`, which
is the existing declaration mechanism: a skill says which hosts it will reach,
the workspace's egress rules say which it may, and the difference surfaces as
`unmet_hosts`. So a freshly generated skill arrives already saying what it
needs, and the workspace is shown exactly what to allow.

It also reads `securitySchemes`, and records **the name of the header the API
expects** -- never a value, which the specification does not contain anyway.
That is enough to pre-fill an egress rule's `header` field, leaving the
workspace to supply only the environment variable holding the secret. The
credential itself never touches the wizard, the skill or the specification, as
[integrations.md](integrations.md) requires.

## Where it runs

An API endpoint, with the existing skills UI around it. A workspace supplies a
specification -- a URL to fetch or a file to upload -- and receives a proposed
skill to review and save.

Proposed rather than saved, because a generated skill is a draft. The workspace
sees the manifest it is about to carry on every turn, and the host list it is
about to be asked to allow, before either becomes real.

**Parsing is the hazardous part.** A specification is untrusted input from a
workspace, parsed in the API tier, and the failure modes are the ordinary ones
for structured formats: deeply nested structures, enormous documents, `$ref`
cycles. Bound the document size, bound the recursion depth when resolving
references, refuse rather than truncate, and do it before any of it is
rendered.

A URL fetch is the other hazard, and it has an answer already: fetching a
specification from a host is reaching a host on a workspace's behalf, which is
what the gateway is for and what the egress rules govern. It is not a new path
-- the API asks the gateway, exactly as an agent's `fetch_url` does. Uploading
a file avoids the question entirely and should be the path that works first.

## What this does not do

**It does not generate tool definitions.** The output is prose an agent reads
and composes `fetch_url` from. If that turns out not to be enough --
[roadmap.md](roadmap.md) describes when it might not be -- the same parsed
specification produces tool definitions instead, and only the consumer changes.
The manifest-and-detail split survives either way.

**It does not constrain what the agent sends.** A conduit operation -- one
whose arguments decide who is reached rather than what is read -- cannot be
made safe by documentation. That needs argument constraints, which prose cannot
express, and is the strongest argument in the fork.

**It does not validate the specification against the running service.** A
document that lies about its own API produces a skill that lies about it too.
Evaluation is what catches that, by calling the thing and seeing what happens.
